SOLID

Cinco princípios para código orientado a objetos

O que é SOLID

Um conjunto de cinco princípios de design orientado a objetos, popularizado por Robert C. Martin (Uncle Bob). O objetivo é ter código mais fácil de entender, testar e alterar.

S
Single Responsibility
Responsabilidade Única

L

S

Single Responsibility Principle

(Princípio da Responsabilidade Única)

Uma classe deve ter apenas um motivo para mudar. Se ela gera, salva e envia o relatório, qualquer mudança em uma dessas tarefas mexe na classe inteira.

Dica

Se para descrever a classe você usa "e" (gera e salva e envia), ela provavelmente faz coisas demais.

// Errado: uma classe com três responsabilidades
class Relatorio {
    public function gerar(): string { /* ... */ }
    public function salvarPdf(string $texto): void { /* ... */ }
    public function enviarEmail(string $para): void { /* ... */ }
}

// Certo: cada classe cuida de uma tarefa
class Relatorio {
    public function gerar(): string { /* ... */ }
}
class ExportadorPdf {
    public function salvar(string $texto): void { /* ... */ }
}
class EnviadorEmail {
    public function enviar(string $para): void { /* ... */ }
}
O

Open/Closed Principle

(Princípio Aberto/Fechado)

Aberto para extensão, fechado para modificação. Para adicionar um comportamento novo, você cria código novo em vez de editar o que já funciona.

Dica

Um if/elseif que cresce a cada novidade é sinal de que falta uma interface.

// Errado: todo desconto novo exige editar este if
if ($tipo === 'blackfriday') { $total *= 0.7; }
elseif ($tipo === 'cupom10') { $total -= 10; }

// Certo: cada desconto é uma classe
interface Desconto {
    public function aplicar(float $total): float;
}
class DescontoBlackFriday implements Desconto {
    public function aplicar(float $total): float {
        return $total * 0.7;
    }
}
// Novo desconto? Crie outra classe. O Carrinho não muda.
class Carrinho {
    public function total(float $valor, Desconto $desconto): float {
        return $desconto->aplicar($valor);
    }
}
L

Liskov Substitution Principle

(Princípio da Substituição de Liskov)

Uma classe filha deve poder substituir a classe pai sem quebrar o programa. Quem usa o pai não pode ter surpresas com o filho.

Dica

Se o filho precisa lançar exceção ou deixar um método vazio para "desligar" algo do pai, a herança está errada.

class Ave {
    public function comer(): void { /* ... */ }
}
class AveQueVoa extends Ave {
    public function voar(): void { /* ... */ }
}
class Pardal extends AveQueVoa { }
class Pinguim extends Ave { } // pinguim não voa

function soltar(AveQueVoa $ave): void {
    $ave->voar(); // qualquer AveQueVoa funciona aqui
}

// Errado: Pinguim extends AveQueVoa com um voar()
// que lança exceção. soltar(new Pinguim) quebraria.
I

Interface Segregation Principle

(Princípio da Segregação de Interfaces)

Nenhuma classe deve ser obrigada a implementar métodos que não usa. Prefira várias interfaces pequenas a uma interface grande.

Dica

Métodos implementados vazios ou só com throw indicam uma interface grande demais.

// Errado: toda impressora precisa digitalizar e ter fax
interface MaquinaEscritorio {
    public function imprimir(): void;
    public function digitalizar(): void;
    public function enviarFax(): void;
}

// Certo: interfaces pequenas e específicas
interface Impressora { public function imprimir(): void; }
interface Scanner    { public function digitalizar(): void; }

class ImpressoraSimples implements Impressora {
    public function imprimir(): void { /* ... */ }
}
class Multifuncional implements Impressora, Scanner {
    public function imprimir(): void { /* ... */ }
    public function digitalizar(): void { /* ... */ }
}
D

Dependency Inversion Principle

(Princípio da Inversão de Dependência)

Classes de alto nível não devem depender de classes concretas, e sim de abstrações (interfaces). Assim fica fácil trocar a implementação.

Dica

Trocar ArquivoLogger por um logger de banco de dados não exige nenhuma mudança no PedidoService.

interface Logger {
    public function registrar(string $msg): void;
}
class ArquivoLogger implements Logger {
    public function registrar(string $msg): void {
        file_put_contents('app.log', $msg . PHP_EOL, FILE_APPEND);
    }
}
class PedidoService {
    private Logger $logger;
    // Depende da interface, não da classe concreta
    public function __construct(Logger $logger) {
        $this->logger = $logger;
    }
    public function finalizar(int $id): void {
        $this->logger->registrar("Pedido $id finalizado");
    }
}

PSRs

Padrões recomendados pela comunidade PHP

O que são PSRs

PSR
PHP Standards Recommendation

Recomendações publicadas pelo PHP-FIG (PHP Framework Interop Group) para padronizar como escrevemos e organizamos código PHP.

Por que seguir
1
Qualquer dev PHP lê o seu código sem estranhar
2
Bibliotecas e frameworks funcionam bem juntos
3
Ferramentas como PHP_CodeSniffer verificam o padrão automaticamente

PSR-1: Basic Coding Standard

(Padrão Básico de Codificação)
1
Use somente as tags <?php ou <?=
<?php
2
Arquivos em UTF-8 sem BOM
UTF-8
3
Um arquivo declara classes e funções OU executa código, nunca os dois
class Usuario { } / echo 'oi';
4
Namespaces e classes seguem o padrão de autoload (PSR-4)
App\Model\Usuario
5
Nomes de classes em StudlyCaps (PascalCase)
ContaBancaria
6
Constantes em maiúsculas, separadas por underline
TAXA_SAQUE
7
Métodos em camelCase
depositar()

PSR-1 na Prática

Tag e namespace
Abre com <?php e o namespace segue a pasta
Classe
ContaBancaria em StudlyCaps
Constante
TAXA_SAQUE em maiúsculas
Métodos
depositar() e sacar() em camelCase
<?php
// src/Model/ContaBancaria.php
namespace App\Model;

class ContaBancaria
{
    const TAXA_SAQUE = 2.5;

    private float $saldo = 0;

    public function depositar(float $valor): void
    {
        $this->saldo += $valor;
    }

    public function sacar(float $valor): void
    {
        $this->saldo -= $valor + self::TAXA_SAQUE;
    }
}

Composer

O gerenciador de dependências do PHP. Instala bibliotecas de terceiros e gera o autoload que carrega suas classes automaticamente (PSR-4).

composer.json
Lista as dependências do projeto e suas versões
vendor/
Pasta onde as bibliotecas instaladas ficam
autoload.php
Um require e todas as classes ficam disponíveis
# Terminal
$ composer require monolog/monolog
$ composer install
<?php
require 'vendor/autoload.php';

use Monolog\Logger;

$log = new Logger('app');

Docker

O mesmo ambiente PHP em qualquer máquina

O que é Docker

Uma ferramenta que empacota sua aplicação com tudo o que ela precisa (PHP, extensões, servidor web e configurações) e roda do mesmo jeito em qualquer computador.

Imagem
A receita: um modelo pronto do ambiente
Container
A receita em execução, isolada do resto do sistema
# Dockerfile
FROM php:7.4-apache

RUN docker-php-ext-install pdo_mysql

COPY . /var/www/html/
# Terminal
$ docker build -t minha-app .
$ docker run -p 8080:80 minha-app

Por que usar Docker

01
Fim do "na minha máquina funciona"
Todo o time usa exatamente o mesmo ambiente.
02
Versões lado a lado
Um projeto em PHP 7.4 e outro em PHP 8 no mesmo computador.
03
Começar rápido
Um novo dev sobe o projeto com um único comando.
04
Serviços sem instalação
MySQL, Redis e outros rodam como containers.
